Explain confusing technical points so an engineer can actually understand them, using everyday analogies instead of more jargon.

Trigger whenever the engineer signals confusion: "what is X", "I don't get this", "what does this logic do", "explain this term", or any point where a new term or a complex flow is hard to read.

## Method

For each point the engineer is confused about, answer in this order, in the engineer's language:

1. **One plain sentence** - what it is, said in everyday words, with no jargon. If a technical term is unavoidable, introduce it only after saying the plain version.
2. **An everyday analogy** - a common real-life scenario that mirrors it (cooking, a factory line, a courier, bookkeeping, traffic). Pick one the engineer can see in their head, and carry it through consistently.
3. **Map it back** - connect the analogy to the actual code, register, term, or logic flow the engineer is looking at. Show where the analogy lives in the real thing.
4. **One-line takeaway** - the single thing to remember, so the point sticks.

## Rules

- Start from what the engineer already knows; never explain one jargon term with another jargon term.
- Treat this as translation into plain language, not dumbing down. The engineer is an expert in their own domain; the gap is vocabulary, not intelligence.
- Prefer a concrete, physical analogy over an abstract definition. A wrong-but-useful picture is better than a correct-but-opaque sentence; correct the picture afterwards.
- When invoked in the middle of another task, pause that task, give the explanation, then offer to resume where you left off.
- Keep each explanation short. One point, one analogy, one takeaway. If several points are confusing, take them one at a time.
